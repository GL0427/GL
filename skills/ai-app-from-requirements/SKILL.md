# 从需求到可用 App

把模糊想法逐步收敛成可运行、可验收、可交接的第一版 App。采用视频演示的顺序：**需求与页面结构 → 设计风格 → 产品需求文档 → 开发计划 → 第一版实现 → 功能验收与源码归档 → 按需部署和安装**。

## 工作方式

- 先了解用户要解决的问题、目标用户、使用设备和成功标准。沿用用户指定的技术栈与开发工具；没有指定时，先检查现有项目和可用环境，再选择最简单且适合目标平台的实现方式。
- 把每个阶段的产物做成可检查的结果。需求、页面结构和关键交互尚未明确时，先提问或列出假设供确认，不要用一大段提示词直接跳到编码。
- 优先做范围明确的第一版。把后续想法列为待办，不擅自扩大功能范围。
- 不把网页预览称为手机真机验证，不把本地运行称为已部署。部署、公开分享、账号配置和外部服务变更，只在用户提出时进行。

## 流程

### 1. 写需求提示词，确定页面结构

先将想法整理为一份短需求说明，覆盖：

- App 名称、目标用户、要解决的问题和主要使用场景
- 第一版必须完成的核心任务，以及明确不做的内容
- 页面清单、每页展示的信息、用户操作和页面间跳转
- 需要保存的数据、保存位置、数据生命周期和隐私要求
- 空状态、错误状态、边界情况和验收方式

根据使用场景画出页面与操作顺序。请用户确认页面结构和关键交互后再进入实现。若需求有歧义，指出具体问题并给出简短选项；不要默默把建议当成用户决定。

### 2. 确定设计风格

把风格写成能指导界面的具体约束：视觉参考、主辅色、字体层级、卡片与按钮形态、留白、图表风格，以及手机和桌面布局的优先级。先生成一版供用户查看，再根据反馈调整。不要只写“高级、简洁、好看”而没有可执行描述。

### 3. 整理产品需求文档（PRD）

把已确认的需求、页面、交互、视觉约束、数据规则和验收条件整理到项目文档中。确保文档能回答：每个页面如何进入、用户能做什么、数据如何变化、刷新或重开后会怎样。将未决事项显式标为待确认。

### 4. 制定开发计划

检查项目目录和已有代码，再按依赖关系拆分实现步骤。先做核心用户流程和数据保存，再做统计、图表、个性化和打磨。每项计划写清修改范围与完成条件。已有项目时先理解结构，不覆盖或重建无关文件。

### 5. 实现第一版 App

按计划逐项实现，并运行本地预览。每轮集中解决一组相关问题；出现页面或行为与确认需求不符时，回到需求和验收条件修正。保留用户已有数据和代码。不要仅凭代码生成成功就宣称功能完成。

### 6. 功能验收

对照 PRD 验证每条核心流程，并报告实际检查的范围。至少关注：

- 核心页面和导航能否使用
- 新建、编辑、完成、删除等操作是否正确（仅检查产品确实包含的操作）
- 数据刷新或重开后是否仍在，备份与恢复是否按约定工作
- 空状态、无效输入和取消操作是否处理妥当
- 手机与桌面布局是否适配目标设备

若没有执行浏览器、自动化或真机验证，要明确说明未验证的部分；不要把推断写成测试结果。

### 7. 留存源码；按需部署和安装

整理源码、依赖说明、启动方式、需求文档和验收记录，使用用户指定的版本控制或归档方式保存。若用户希望手机使用，先确认目标是手机浏览器、可安装 PWA 还是原生 App，再说明所需部署和 HTTPS 条件。部署或公开分享之前，核对目标环境和用户授权；完成后实际打开线上地址或安装产物验证，再报告结果。

## 视频中的示例

演示以健身记录 App「今天练了吗」为例：训练计划 → 开始训练 → 选择动作并逐组记录 → 完成训练 → 查看记录和进步；另有个人设置。视频要求数据保存在本地、重开后保留，并提到备份恢复；视觉方向是简洁、舒适、浅色搭配少量绿色、圆角卡片和清晰图表，优先适配手机并兼顾桌面。该示例用于说明如何把需求落成页面和验收条件，不是每个新 App 都必须照搬的功能或风格。
